# Kubernetes pod and service discovery jobs

Status: ready-for-agent

## Parent

`.scratch/prometheus-scrape-templating/spec.md` — "Service-discovery jobs"

## What to build

The two Kubernetes service-discovery jobs that exist in every deployment, generated by the
chart from a single namespace list. Each sits behind its own enable flag, carries its own
chart-owned `metric_relabel_configs` block, and can have that block extended or replaced.

```yaml
prometheus:
  mapcolonies:
    scrape:
      kubernetes:
        namespaces: []         # own namespace always included; empty means own only
        pod:
          enabled: true
          builtinMetricRelabelConfigs: true
          extraMetricRelabelConfigs: []
        service:
          enabled: true
          builtinMetricRelabelConfigs: true
          extraMetricRelabelConfigs: []
```

### Job names are load-bearing

The jobs must be named exactly `k8s-scrape` (pod) and `k8s-svc-scrape` (service). Alert
expressions in site-values reference `job="k8s-svc-scrape"` directly, so a renamed job
silently breaks alerts. These two names are chart-owned constants, not values.

### One namespace list, both jobs

Both jobs receive the same list, which is what makes it impossible for them to drift apart —
the current site-values has exactly that bug in one environment, where the pod job and the
service job watch different namespace sets. The list does not need to repeat the release
namespace.

### Own-namespace confinement is an invariant, not a default

`own_namespace: true` is emitted unconditionally and is not exposed as a value. No
combination of inputs may cause the `namespaces` block to be omitted, or emitted without it.

This matters because in Kubernetes service discovery an absent or empty namespace restriction
means *all* namespaces, and these clusters do not grant the cluster-scoped RBAC that would
require — so a job that escaped the restriction would not fail loudly, it would collect 403s
and discover nothing. An empty namespace list therefore means own-namespace-only, which is
both the default and the floor.

### Discovery scaffolding

Each job carries the annotation-driven `relabel_configs` chain: keep on
`prometheus.io/scrape`, drop on `prometheus.io/scrape_slow`, scheme and metrics-path and port
from annotations, `prometheus.io/param_*` mapped to query parameters, Kubernetes labels
mapped through, Alloy-specific leaked labels dropped, namespace and instance labels set. The
pod job additionally drops targets in terminal pod phases and drops the `path` label; the
service job's chain reads service annotations rather than pod ones and takes `instance` from
the service name.

Copy these verbatim from the current site-values rather than rewriting them — the source is
`infra/prometheus/{dev,prod}/alerts-values.yaml` on the site-values repo's `origin/master`.
The two environments are identical here apart from their namespace lists. Be aware that a
local site-values checkout may be on a branch that predates these rules; read them from
`origin/master`.

### Chart-owned metric relabel rules

Both jobs share a high-cardinality `labeldrop` (`pod_template_hash`, `uid`, `ip`, `pod_ip`,
`container_id`, `image_id`, `helm_sh_chart`, `app_kubernetes_io_managed_by`, `trace_id`,
`span_id`, `request_id`, `transaction_id`, `client_ip`, `remote_addr`, `user_id`,
`session_id`, `controller_revision_hash`).

Beyond that the two differ: the pod job drops unused histogram-bucket series for the log,
trace and collector components — Loki request/response and memcache and
frontend/kv/index/cache/boltdb and TSDB-shipper buckets, Tempo response buckets, OTel
Collector batch-processor buckets, plus Node.js GC, bundle-loading and Grafana
response-size buckets — while deliberately keeping `loki_ingester_*_bucket` and
`tempo_request_*_bucket`, which dashboards use. The service job drops unused
kube-state-metrics families: all `kube_replicaset_*`, selected `kube_pod_*` metadata,
`kube_deployment_status_condition`, and all `kube_secret_*` / `kube_configmap_*` except the
`_info` series. Only `_bucket` series are dropped; matching `_sum` and `_count` series stay.
These are ~120 lines that are byte-identical between the two environments today, which is why
they belong to the chart. Copy them verbatim, comments included, from the same source.

### Extending and replacing the rules

Each job reads its own append key, independently of the other, because the two jobs drop
different metric families. Appended rules run **after** the chart's own, which means they can
drop further but can never recover a series the chart has already dropped — relabelling is
one-way.

The common case needs nothing more: dropping metrics for a component a site does not run is a
no-op. But a site that *does* run that component and genuinely needs one of the dropped
series would otherwise have no recourse short of a chart release, or abandoning the generated
job entirely. Each job therefore also carries a flag that turns the chart-owned block off, at
which point the append key becomes the whole list. It defaults to on.

### Documentation

Document every key this slice adds — full values path, type, default, effect — including each
of the four per-job keys and the shared namespace list. Two things a reader cannot infer from
the key list and must be told:

- What the chart's own drop rules actually drop, per job, at a level of detail that lets a site
  decide whether a series it needs is at risk. List the metric families, not just "cardinality
  rules", and name the deliberate keeps (`loki_ingester_*_bucket`, `tempo_request_*_bucket`).
- That appended rules run after the chart's and can only drop further, never recover, so
  recovering a series means turning the builtin block off for that job and supplying the whole
  list — and that this is exactly what the flag is for.

Also state that own-namespace confinement is not configurable and why: the failure mode of an
escaped restriction is silent (403s and no targets), not loud. And note that an empty namespace
list is not "no restriction" but "own namespace only".

Include a worked example: a namespace list plus one appended rule, and the rendered job it
produces.

## Acceptance criteria

- [ ] Default values render both jobs, named exactly `k8s-scrape` and `k8s-svc-scrape`.
- [ ] Both jobs' `kubernetes_sd_configs` carry the same namespace list, drawn from one values
      key, plus `own_namespace: true`.
- [ ] `own_namespace: true` is present in every render: with an empty namespace list, with a
      populated one, and with any combination of the other flags. No value can remove it or
      omit the `namespaces` block.
- [ ] An empty namespace list renders a job restricted to the release's own namespace, not a
      cluster-wide one.
- [ ] Each job's enable flag independently removes only that job.
- [ ] With defaults, each job's `metric_relabel_configs` matches the current site-values
      rules for that job, compared as parsed data.
- [ ] Appended rules for one job appear after the chart's own rules in that job and do not
      appear in the other job.
- [ ] Turning a job's builtin-rules flag off leaves only that job's appended rules as its
      whole `metric_relabel_configs`, and leaves the other job's rules untouched.
- [ ] Every values key this slice adds is documented in the README with its full path, type,
      default and effect, including all four per-job keys and the shared namespace list.
- [ ] The README lists what the chart's drop rules drop per job and which series are
      deliberately kept, states that appended rules cannot recover an already-dropped series,
      and explains that own-namespace confinement is not configurable and why an empty
      namespace list means own-namespace-only rather than unrestricted.
- [ ] The README shows a worked example with a namespace list and an appended rule, and the
      job it renders.
